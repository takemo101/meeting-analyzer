# 検証手順と記録

[SPEC.md](../SPEC.md) の受け入れ条件（A01〜A16）を、どう観測し、何をいつ確認し、何が人間の確認待ちかを記す。新しい合格条件は作らない。実施の権限は、ここからは推測せず、依頼で判断する。実機の検証は、[macOS 共通検証スキル](../.agents/skills/verifying-macos-apps/SKILL.md) と [固有レシピ](../.agents/skills/verifying-meeting-analyzer/SKILL.md) に従う。

## 証拠の種類

次を混ぜない。一つの種類の成功を、別の種類の成功として扱わない。

| 種類 | 例 | 何を示すか |
|---|---|---|
| ソース確認 | コードを読んだ | 実装がそう書かれていること。動作は示さない |
| ビルド | `./scripts/build.sh` が成功 | コンパイルとバンドル作成。動作は示さない |
| 単体テスト | `./scripts/test.sh`（Swift Testing）の pass | 音声・画面に依存しない規則の入出力（まとめ方・状態遷移・記録・出来事の JSON の形・窓口（実際の Unix ドメインソケット）・MCP の JSON-RPC・失敗の分類・引数の解釈・再生の流れ・`LiveSession` の流れ） |
| 自動の実機観測 | `scripts/native-e2e.swift` の pass | 自分で起動した候補の、実行ファイルの CLI（終了コード・標準出力・標準エラー）、**本物のオンデバイス認識**（`say` で作った日本語音声）、**本物の窓口と MCP サーバー**（このハーネスが、MCP の JSON-RPC を話す）が渡す出来事、書き出された記録ファイル、メニューバーのアプリの起動・窓口・終了 |
| 人間の確認 | マイク・システム音声の実取り込み、権限、回り込み、実会議の認識の品質、各エージェントでの連携とサマリー | ユーザーが実機で見て判断したこと |

## 検証の入口

リポジトリのルートで実行する。

```sh
just test         # ./scripts/test.sh と同じ。単体テスト
just e2e          # ./scripts/e2e.sh と同じ。ビルドし、bundle ID を変えたコピーで全ケースを実行する
```

単体テストは、`./scripts/test.sh`（`swift test` に、Swift Testing のマクロプラグインのパスを渡す。Command Line Tools だけの環境では、SwiftPM が渡さないため）で実行する。XCTest は使わない（Command Line Tools に含まれない）。

ハーネスを直接実行するときは、bundle ID を変えたコピーを用意して渡す（`scripts/e2e.sh` の中身を参照）：

```sh
/usr/bin/swift scripts/native-e2e.swift "$PWD/build/MeetingAnalyzerE2E.app/Contents/MacOS/MeetingAnalyzer" --artifacts "$PWD/build/native-e2e"
```

- `--artifacts` を省略すると `build/native-e2e/` を使う。実行ごとに一意の `run-<日時>/` を 0700 で作り、`report.json`（0600）、検証用の音声（`sample.aiff`）、書き出された記録（`data/sessions/…`）を置く。`build/` は Git 対象外。
- 終了コードは、fail があれば 1、なければ blocked があれば 77、全 pass なら 0。stdout の「今回の report」を読む。部分成功を総合成功へ広げない。
- **前提**：`say` と日本語の声 Kyoko、`ja_JP` のオンデバイス認識（`doctor` で確認）。足りなければ、該当のケースは **blocked**（合格にしない）。
- ハーネスは、**使っているアプリのデータ・窓口に触れない**。データの置き場所（`MEETING_ANALYZER_DATA_DIR`）と窓口のソケット（`MEETING_ANALYZER_SOCKET`。パスが短い `/tmp/ma-e2e-<乱数>/`）を、検証用に向け、bundle ID を変えたコピー（`dev.takemo101.meeting-analyzer.e2e`）で実行する。
- ハーネスは、権限の要求 API を呼ばない。マイク・画面収録の許可を必要とするケースは、まだ無い（取り込みを伴う操作は、人間の確認。下記）。実行中にマウス・キーボードを使わせるケースも、いまは無い。`e2e.sh` は、毎回 `build.sh` で作り直してから実行する（古いビルドに対する成功を、現在のソースの成功と取り違えないため。再ビルドせずに古いビルドへ実行した例が、2026-10-22 の記録にある）。
- 起動するのは、自分で作った実行ファイル（`replay`・`mcp`・アプリ）だけ。自分が起動した PID だけを、PID で終了させる。エージェント（Claude Code など）は起動しない。

### 自動では観測しないもの

- メニューの見た目と、取り込みを伴う操作（開始〜終了）。メニューの構造・開始の失敗のダイアログ（同意のダイアログは、のちに廃止）は、アクセシビリティ（AX）で観測したが（下記の実施記録）、ハーネスのケースにはしていない。
- マイク・システム音声・画面の実取り込み、権限の許可。
- 認識の品質（会議の音声・複数人・専門用語）、遅延、回り込み。
- 各エージェントでの連携（Claude Code の `--channel` の押し込みを含む）とサマリーの内容。

## 人間の確認

AI はこれらを合格にしない。取り込みとメニューの操作は実装済みで、次の手順で人間が確認する（結果は、実施記録へ）。

| 項目 | 受け入れ条件 | 確認すること（予定） |
|---|---|---|
| マイクの取り込みと権限 | A10 | `just run` で起動し、メニューで「マイク」をオン、「開始」。**初回に、マイクの許可の確認が OS から出る**。許可すると、メニューバーの絵が「取り込み中」になり、話すと「本人」の字幕が届く。拒否したときは、「会議を始められません」のダイアログで理由が出て、待機のまま |
| システム音声の取り込み | A11 | 「システム音声」を「全体」にして開始：**初回に画面収録の許可の確認が出る**。Mac から出る音（動画など）が「相手」として届く。アプリ（例：Safari）を選んで開始：そのアプリの音だけが届き、別のアプリの音は混ざらない |
| 回り込み（エコー） | A12 | スピーカーで聞いても、相手の発言が「本人」にならない。`CaptureProbe --mic --app <bundleID> --request` で、先に測れる。効かないときのヘッドホンの案内は、未実装 |
| 会議での認識の品質・遅延 | A04 | 実際の会議で、専門用語・重なる発話・早口がどこまで読めるか。話してから、エージェントへ届くまでの体感 |
| 画面の取り込み | A13 | 撮影の権限、動画の一部の変化も送られること、会議が別ウィンドウでも撮れること |
| 署名と権限 | SPEC §9 | ad-hoc 署名のビルドで、許可がビルドのたびに外れるか |
| エージェント連携とサマリー | A16・A17 | Claude Code・omp・pi・agy・opencode に `mcp` を登録して、字幕が届き（`--channel` の押し込みは Claude Code）、終了の出来事で、詳細なサマリーが出る。サマリーの出来（決定事項・アクション・プロジェクトへの影響の的確さ）。**Claude Code の `get_events` は、合成音声で確認済み**（実施記録） |
| メニューの操作 | A14 | 開始 → 一時停止（絵が変わる・字幕が止まる）→ 再開（時刻が続く）→ 会議を終了（エージェントに終了の出来事が届き、`transcript.md` が書かれる）。「エージェント: N 件接続中」が、`mcp` の起動・終了で増減する。取り込み先のアプリを終了させたとき、メニューに「システム音声の取り込みが止まりました」が出る。アプリの終了（メニュー・SIGTERM）で、`appQuit` で終わる |

- **残る制約・未実施**：マイク・システム音声・画面の取り込み（未実装）、権限、回り込み、実会議の音声での品質と遅延、メニューの操作、エージェント連携とサマリー（live-support 側の変更が先に要る）、ad-hoc 署名での権限の持続、opencode v2 の方式の調査。`say` の音声は、きれいな合成音声であり、実会議の音声より認識しやすい。この記録を、実会議での品質の証拠として使わない。

### 2026-10-22 — 取り込みの試作（A10〜A12 の前段。アプリへは未接続）

- **対象**：`Capture/`（`MicrophoneCapture`・`SystemAudioCapture`）、`Transcription/LiveTranscription.swift`（ライブ入力の認識）、実験用の実行ファイル `CaptureProbe`（製品の CLI ではない。`swift build` で `.build/debug/CaptureProbe`）。デバッグビルド。環境：macOS 27.0.1、Apple M6、Swift 6.4。この記録は SPEC §8 の状態を変えない（A10〜A12 は、アプリに接続されるまで未実装）。
- **権限の扱い**：`CaptureProbe` は、`--request` なしでは、マイク・画面収録が許可済みでないと止まる（確認だけ。要求 API は呼ばない）。マイクは未許可だったので、**マイクの取り込みと回り込みは未実施**（`--mic` が「未許可」で終了することだけを確認）。画面収録は、実行元のプロセスに許可済みだった（許可の変更・要求はしていない）。
- **ライブ認識の遅延（`say -v Kyoko` の合成音声を、実時間の入力として流した。`--file`）**：`.volatileResults` だけでは、結果が発話の終わり、または入力の終わりまで出なかった（10 秒の 1 文で、最初の結果が 10.8 秒後。3 文＋無音の入力で、最初の文の結果が、その文の終わりの約 7 秒後）。`.fastResults` を足すと、暫定の結果は音声の進行に追従し（遅延 ≈ 0）、確定の遅延は 0.9〜1.6 秒になった。認識結果は、足す前と同じ文だった。ライブ入力には `.fastResults` を使う（ファイルの解析には使っていない）。バッファの大きさ（20・100・400 ms）には、遅延は依存しなかった。
- **システム音声のアプリ単位のフィルタ（ScreenCaptureKit）**：選んだアプリ（QuickTime Player。自分が新しく起動した、無音のインスタンス）だけを取る設定で、別のプロセス（`afplay`）が合成音声を鳴らしている間、取り込んだ音量は **RMS 0.0000** だった。同じ条件で、画面全体のフィルタ（アプリを除外しない）の取り込みでは、`afplay` の音を **RMS 0.098** で取れた。別のアプリの音が、アプリ単位のフィルタに混ざらないことの観測。取り込みの配信は、12 秒で 614 バッファ。
- **未確認**：選んだアプリが実際に鳴らしている音を、取れること（対象のアプリに音を鳴らさせる手段を、自動では用意できなかった。Meet・Zoom・Teams で人間が確認する）。エコー除去の効き、実会議の音声の精度、マイクの遅延、ad-hoc 署名のリビルドでの権限の持続。合成音声は、実会議の音声より認識しやすい。

- **2. モデルの取得・検証**：Qwen3-ASR-0.6B（Q8_0・850 MB）と SenseVoice Small（Q8_0・253 MB）の SHA-256 は、**Hex が固定している値と一致**した。Whisper large-v3-turbo は、現在の `main` が、Hex が固定している版と**別のファイル**（バイト数・SHA-256 が違う）だった＝**取り込むなら、版と SHA-256 を固定する**必要がある。ほかに、Qwen3-ASR-1.7B（2.19 GB）・Fun-ASR-Nano（891 MB）・Moonshine base-ja（77 MB）・Silero VAD v6.2（1.2 MB。SHA-256 一致）を取得した。
- **3. 文字の誤り率（CER。1 文ずつ・12 文・309 字。小さいほど良い）と、1 文（約 5 秒）あたりの処理時間**（M6・Metal・モデル読み込み済み）：

| モデル（Q8_0） | 大きさ | きれい | 電話帯域 | 雑音 10 dB | 雑音 5 dB | 5 秒の文の処理 | 実時間比 |
|---|---:|---:|---:|---:|---:|---:|---:|

| Qwen3-ASR-0.6B | 850 MB | 0.016 | 0.029 | 0.039 | 0.107 | 0.15 秒 | 約 32 倍 |

  - 「雑音」は、合成音声に、白色の雑音を、指定の信号対雑音比で足した（本物の雑音ではない）。「電話帯域」は、300〜3400 Hz に絞り、8 kHz を経由した。男性の声（Otoya）で作る予定だった変種は、その声が無く、同じ声に落ちた（結果が、きれいな音声と同一）ので、**使っていない**。
  - **1 本まるごと（39 秒・59 秒）を 1 回で渡すと、Qwen3-ASR-0.6B（CER 0.05〜0.09）と SenseVoice（0.17〜0.22。文を落とす）が悪化し、Moonshine は 39 秒で、不正な文字列を出して失敗した**（Whisper・Fun-ASR・Qwen3-ASR-1.7B は 0.0〜0.03）。**どのモデルも、VAD で発話ごとに区切って渡すのが前提**。
- **4. リアルタイム性**：transcribe.cpp の、Qwen3-ASR・Whisper・SenseVoice・Fun-ASR・Moonshine-ja は、**ストリーミング非対応**（カタログの `streaming: false`）。つまり、**話している途中の暫定の文字（Apple 標準の volatile な結果）は出ない**。代わりに、**Silero VAD で発話を区切り、区切れたら、その発話を 1 回で文字にする**形になる。VAD は、CPU で約 4,000 倍速（77 秒の音声を 19 ms）。77 秒（12 文、文の間に 1.5 秒の無音）を、17 区間に分けた（文の途中の短い間でも切れるので、**区間を結合する規則が要る**）。字幕の遅れの見込みは、「話し終わってから、無音の判定（0.5〜1 秒程度。要調整）＋ 0.15〜0.5 秒」（Apple 標準は、実機の合成音声で、確定まで 0.9〜1.6 秒）。**この見込みは、組み合わせた実測ではない**（VAD と認識を、別々に測った）。
- **5. Swift からの利用**：`transcribe.h`（C API）を、SwiftPM の実行ファイル（Swift 6 の道具・Swift 5 モード）から、**静的ライブラリを `-force_load` でリンクして**直接呼べた（Qwen3-ASR・Whisper・Fun-ASR で、CLI と同じ文字・同じ速さ）。公式の Swift バインディング（`bindings/swift`、macOS 13 以降）もあるが、配布は **`.xcframework`（動的フレームワーク）で、作成には `xcodebuild` が要る**（この Mac は Command Line Tools だけなので作れない＝CI の macOS ランナーで作る想定）。静的ライブラリを素直にリンクすると、Objective-C の実行時情報の問題があるため、`-force_load` か動的フレームワークが要る（公式スクリプトの注記）。初回のモデル読み込みは、約 4.5 秒（ファイルの読み込み・Metal の準備。2 回目以降は 0.1〜0.2 秒）。
- **6. ライセンス**：transcribe.cpp は MIT、Qwen3-ASR は Apache-2.0、Whisper は MIT。**SenseVoice・Fun-ASR は FunASR のモデルライセンス、Moonshine は独自のコミュニティライセンス**＝取り込む（配布・ダウンロードを案内する）前に、条件の確認が要る。
- **結論（PoC として）**：**技術的には可能**（ビルド・Swift からの呼び出し・日本語の認識・速度は、すべて確認できた）。ただし、(a) きれいな音声では、Apple 標準と大差が無い（むしろ Apple が同等以上）。(b) **雑音が強い条件では、Whisper large-v3-turbo と Qwen3-ASR-1.7B が、Apple 標準より誤りが少なかった**（雑音 5 dB：0.045・0.055 対 0.091）。(c) 暫定の文字が出ない。(d) 外部依存（C++ のライブラリ）・ネットワーク（モデルの取得）・容量（数百 MB〜2 GB）が増え、仕様の変更が要る。
- **この PoC で、決められないこと**：**精度の優劣**。合成音声・12 文・309 字で、実会議の音声（話者の癖・複数人・間・英語混じり・固有名詞・エコー・本物の雑音）ではない。差が数文字のところは、誤差の範囲。**実会議の音声での比較が要る**。
