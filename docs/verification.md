# 検証手順と記録

[SPEC.md](../SPEC.md) の受け入れ条件（A01〜A16）を、どう観測し、何をいつ確認し、何が人間の確認待ちかを記す。新しい合格条件は作らない。実施の権限は、ここからは推測せず、依頼で判断する。実機の検証は、[macOS 共通検証スキル](../.agents/skills/verifying-macos-apps/SKILL.md) と [固有レシピ](../.agents/skills/verifying-meeting-analyzer/SKILL.md) に従う。

## 証拠の種類

次を混ぜない。一つの種類の成功を、別の種類の成功として扱わない。

| 種類 | 例 | 何を示すか |
|---|---|---|
| ソース確認 | コードを読んだ | 実装がそう書かれていること。動作は示さない |
| ビルド | `./scripts/build.sh` が成功 | コンパイルとバンドル作成。動作は示さない |
| 単体テスト | `./scripts/test.sh`（Swift Testing）の pass | 音声・画面・ネットワークに依存しない規則の入出力（まとめ方・状態遷移・記録・JSON の形・送り先の検査・失敗の分類・引数の解釈・再生の流れ） |
| 自動の実機観測 | `scripts/native-e2e.swift` の pass | 自分で起動した候補の、実行ファイルの CLI（終了コード・標準出力・標準エラー）、**本物のオンデバイス認識**（`say` で作った日本語音声）、偽のブリッジが受け取った HTTP 要求、書き出された記録ファイル、メニューバーのアプリとしての起動と終了 |
| 人間の確認 | マイク・システム音声の実取り込み、権限、回り込み、会議での認識の品質、各エージェントでの連携とサマリー | ユーザーが実機で見て判断したこと |

## 検証の入口

リポジトリのルートで実行する。

```sh
just test         # ./scripts/test.sh と同じ。単体テスト
just e2e          # ./scripts/e2e.sh と同じ。ビルドし、bundle ID を変えたコピーで全ケースを実行する
```

単体テストは、`./scripts/test.sh`（`swift test` に、Swift Testing のマクロプラグインのパスを渡す。Command Line Tools だけの環境では、SwiftPM が渡さないため）で実行する。XCTest は使わない（Command Line Tools に含まれない）。

ハーネスを直接実行するときは、bundle ID を変えたコピーを用意して渡す（`scripts/e2e.sh` の中身を参照）：

```sh
/usr/bin/swift scripts/native-e2e.swift "$PWD/build/MeetingAnalyzerE2E.app/Contents/MacOS/MeetingAnalyzer" --artifacts "$PWD/build/native-e2e"
```

- `--artifacts` を省略すると `build/native-e2e/` を使う。実行ごとに一意の `run-<日時>/` を 0700 で作り、`report.json`（0600）、各ケースの偽のブリッジの記録（`<ケース>-bridge.jsonl`）、検証用の音声（`sample.aiff`）、書き出された記録（`data/sessions/…`）を置く。`build/` は Git 対象外。
- 終了コードは、fail があれば 1、なければ blocked があれば 77、全 pass なら 0。stdout の「今回の report」を読む。部分成功を総合成功へ広げない。
- **前提**：`node`（偽のブリッジ）、`say` と日本語の声 Kyoko、`ja_JP` のオンデバイス認識（`doctor` で確認）。足りなければ、該当のケースは **blocked**（合格にしない）。
- ハーネスは、**使っているアプリのデータ・トークンに触れない**。データの置き場所（`MEETING_ANALYZER_DATA_DIR`）とトークンの置き場所（`LIVE_SUPPORT_RUNTIME_DIR`・`--token-dir`）を、検証用の一時ディレクトリへ向け、トークンは検証用に作る。bundle ID を変えたコピー（`dev.takemo101.meeting-analyzer.e2e`）で実行する。
- ハーネスは、権限の要求 API を呼ばない。マイク・画面収録の許可を必要とするケースは、まだ無い（取り込みが未実装のため）。実行中にマウス・キーボードを使わせるケースも、いまは無い。
- 起動するのは、自分で作った実行ファイルと、偽のブリッジ（`node scripts/e2e-bridge.mjs`）だけ。ケース A1 は、自分が起動した PID だけを、PID で終了させる。

## ケースと受け入れ条件

| ケース | 内容 | 観測 | 受け入れ条件 |
|---|---|---|---|
| Z1 | `--version` | 終了コード 0、標準出力が `meeting-analyzer 0.1.0` | A01 |
| Z2 | 知らないコマンド | 終了コード 1、標準エラーの JSON の `code` が `usage` | A01 |
| Z3 | 読めない音声ファイル（`replay`） | 終了コード 2 | A08 |
| D1 | `doctor` | `supported` と `installed` が真（偽なら blocked） | A04 |
| D2 | 検証用の日本語音声の作成 | `say -v Kyoko` が成功（失敗なら blocked） | — |
| R1 | `replay`（`--speaker others`） | 偽のブリッジが受け取った要求：最初が `/health`、全要求が認証済みで Host が `127.0.0.1:<port>`、`/captions` が 1 件以上、`/end` が最後に 1 件だけ、全応答が 2xx。`sequence` が 1 から連続、`sessionId` が 1 つ、`platform` が `Mac`、`meetingId` が指定どおり、全 `speakerName` が「相手」、認識結果に「リリース」「テスト環境」を含む。`/end` の `reason` が `user`、`batches` が送った数と一致、`utterances` ≥ 1、`durationSeconds` ≥ 1、`transcriptPath` が検証用のデータ置き場所の中にあり、本文に「相手:」と「リリース」を含み、権限が 0600 | A04・A05・A06・A07 |
| R2 | `replay`（`--speaker you`） | R1 と同じ。全 `speakerName` が「あなた」 | A05 |
| R3 | トークン違い | 終了コード 3、`code` が `bridge_unauthorized`、`/health` 以外を送っていない | A08 |
| R4 | ブリッジが無い（ポート 9） | 終了コード 3、`code` が `bridge_unreachable` | A08 |
| R5 | 送り先が `https://example.com` | 終了コード 3、`code` が `endpoint_invalid`（通信する前に断る） | A08 |
| A1 | 引数なしで起動 | 6 秒以内に起動し、1.5 秒後も動いている。`activationPolicy` が `accessory`。通常のウィンドウ（レイヤー 0）が無い。SIGTERM で 5 秒以内に終了 | A09 |

ケースの期待値は、実行する前に決めたもので、結果を見て変えない。ハーネスが、期待を満たさない観測を fail にすることは、変異で確認した（[実施記録](#実施記録)）。

### 自動では観測しないもの

- メニューバーの項目の見た目・メニューの操作（アクセシビリティの許可が要る。メニューの操作が実装されたときに、ケースを足す）。
- マイク・システム音声・画面の実取り込み、権限の許可。
- 認識の品質（会議の音声・複数人・専門用語）、遅延、回り込み。
- 各エージェントでの連携とサマリーの内容。

## 人間の確認

AI はこれらを合格にしない。実装が進んだら、手順を具体化する。

| 項目 | 受け入れ条件 | 確認すること（予定） |
|---|---|---|
| マイクの取り込みと権限 | A10 | 開始の操作で権限の確認が出て、許可すると「あなた」として文字になる。拒否・未許可では、開始せず、理由が出る |
| システム音声の取り込み | A11 | 会議アプリ（Meet・Zoom・Teams）の音声だけが「相手」として文字になり、別のアプリの動画や通知音が混ざらない |
| 回り込み（エコー） | A12 | スピーカーで聞いても、相手の発言が「あなた」にならない。効かないときに、ヘッドホンの案内が出る |
| 会議での認識の品質・遅延 | A04 | 実際の会議で、専門用語・重なる発話・早口がどこまで読めるか。話してから、エージェントへ届くまでの体感 |
| 画面の取り込み | A13 | 撮影の権限、動画の一部の変化も送られること、会議が別ウィンドウでも撮れること |
| 署名と権限 | SPEC §9 | ad-hoc 署名のビルドで、許可がビルドのたびに外れるか |
| エージェント連携とサマリー | A15・A16 | Claude Code・omp・pi・agy（と調査後の opencode v2）で、字幕が届き、終了の合図で、詳細なサマリーが出る。サマリーの出来（決定事項・アクション・プロジェクトへの影響の的確さ） |
| メニューの操作 | A14 | 開始（同意の確認）・一時停止・再開・会議の終了 |

## 実施記録

### 2026-10-22 — 初期の実装（A01〜A09）

- **対象**：v0.1.0、`build/MeetingAnalyzer.app` の実行ファイル（SHA-256 `6eb61f40…434741`。E2E は、bundle ID を変えて再署名したコピーで実行したので、コピーの実行ファイルのハッシュは別）。環境：macOS 27.0.1、Apple M6（arm64）、Swift 6.4（Command Line Tools）。
- **単体テスト**：`./scripts/test.sh` — 49 件・11 スイート pass（最終実行）（まとめ方・状態遷移・記録・JSON の形・送り先の検査・再生の流れと失敗・引数と終了コード・置き場所と権限・版の一致）。
- **native E2E**：`./scripts/e2e.sh` — Z1〜Z3・D1・D2・R1〜R5・A1 の **11 件すべて pass**（pass=11 fail=0 blocked=0）。R1・R2 では、`say -v Kyoko` の音声「来週のリリースの件ですが、テスト環境はいつ使えるでしょうか。」を本物のオンデバイス認識に通し、偽のブリッジが、認証つきで `/health`・`/captions` 1 件・`/end` を受け取り、記録が 0600（ディレクトリ 0700）で書かれたことを観測した。認識結果は入力と一致した。
- **変異による確認**：偽のブリッジを、常に 503 を返すように変えて実行すると、R1・R2 が fail した（終了コード 3 `bridge_not_ready`）。ハーネスが、ブリッジの不調を pass にしないことを確認した。変更は元に戻した。
- **試作での観測（本構成の前）**：`say` の音声で `SpeechTranscriber`（`ja_JP`）を直接呼ぶと、「来週のリリースの件ですが、テスト環境はいつ使えるでしょうか」は正確に読めたが、「Node.js の最新の LTS」は「ノード J S の最新の LDS」と誤認した。確定前の結果は、解析開始から 0.2 秒以内に流れ始めた（ファイルの解析で、実時間ではない）。**専門用語・固有名詞は誤りやすい**（SPEC §3.4）。
- **残る制約・未実施**：マイク・システム音声・画面の取り込み（未実装）、権限、回り込み、実会議の音声での品質と遅延、メニューの操作、エージェント連携とサマリー（live-support 側の変更が先に要る）、ad-hoc 署名での権限の持続、opencode v2 の方式の調査。`say` の音声は、きれいな合成音声であり、実会議の音声より認識しやすい。この記録を、実会議での品質の証拠として使わない。

### 2026-10-22 — 取り込みの試作（A10〜A12 の前段。アプリへは未接続）

- **対象**：`Capture/`（`MicrophoneCapture`・`SystemAudioCapture`）、`Transcription/LiveTranscription.swift`（ライブ入力の認識）、実験用の実行ファイル `CaptureProbe`（製品の CLI ではない。`swift build` で `.build/debug/CaptureProbe`）。デバッグビルド。環境：macOS 27.0.1、Apple M6、Swift 6.4。この記録は SPEC §8 の状態を変えない（A10〜A12 は、アプリに接続されるまで未実装）。
- **権限の扱い**：`CaptureProbe` は、`--request` なしでは、マイク・画面収録が許可済みでないと止まる（確認だけ。要求 API は呼ばない）。マイクは未許可だったので、**マイクの取り込みと回り込みは未実施**（`--mic` が「未許可」で終了することだけを確認）。画面収録は、実行元のプロセスに許可済みだった（許可の変更・要求はしていない）。
- **ライブ認識の遅延（`say -v Kyoko` の合成音声を、実時間の入力として流した。`--file`）**：`.volatileResults` だけでは、結果が発話の終わり、または入力の終わりまで出なかった（10 秒の 1 文で、最初の結果が 10.8 秒後。3 文＋無音の入力で、最初の文の結果が、その文の終わりの約 7 秒後）。`.fastResults` を足すと、暫定の結果は音声の進行に追従し（遅延 ≈ 0）、確定の遅延は 0.9〜1.6 秒になった。認識結果は、足す前と同じ文だった。ライブ入力には `.fastResults` を使う（ファイルの解析には使っていない）。バッファの大きさ（20・100・400 ms）には、遅延は依存しなかった。
- **システム音声のアプリ単位のフィルタ（ScreenCaptureKit）**：選んだアプリ（QuickTime Player。自分が新しく起動した、無音のインスタンス）だけを取る設定で、別のプロセス（`afplay`）が合成音声を鳴らしている間、取り込んだ音量は **RMS 0.0000** だった。同じ条件で、画面全体のフィルタ（アプリを除外しない）の取り込みでは、`afplay` の音を **RMS 0.098** で取れた。別のアプリの音が、アプリ単位のフィルタに混ざらないことの観測。取り込みの配信は、12 秒で 614 バッファ。
- **未確認**：選んだアプリが実際に鳴らしている音を、取れること（対象のアプリに音を鳴らさせる手段を、自動では用意できなかった。Meet・Zoom・Teams で人間が確認する）。エコー除去の効き、実会議の音声の精度、マイクの遅延、ad-hoc 署名のリビルドでの権限の持続。合成音声は、実会議の音声より認識しやすい。
