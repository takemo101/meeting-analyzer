# リファクタリングの観点

既存のコードを見直して、**動作を変えずに**、読みやすく・変えやすくするときの観点と進め方。エージェントに「リファクタリングを見て」と頼むときの土台にする。製品要件は変えない（要件の正本は [SPEC](../SPEC.md)）。設計の原則は [AGENTS.md](../AGENTS.md) の「設計と実装」と [参考にした設計原則](references.md)、Module の責務は [構成説明](architecture.md)。

観点の発想は、[desloppify](https://github.com/peteromallet/desloppify)（コードの品質を、機械的な検出と LLM のレビューで見直すツール。OSNL 0.2）の、主観レビューの観点から借りた。**文章は複製せず、このリポジトリの規則に合わせて書き直している**。ツールは導入していない（Python 製で、状態の保存とスコア化が要るため。外部の依存を足さない方針にも合わない）。

## 進め方

1. **範囲を決める**：1 つの Module、または 1 つの責務。全体を一度に見ない（見る量が増えるほど、指摘が浅くなる）。
2. **観察**：下の観点ごとに、コードを**直接読んで**、根拠（ファイルと行）を集める。ビルドの警告・テストの結果・grep の件数は、**見る場所の目印**で、根拠ではない（目印があっても問題とは限らず、無くても問題はある）。
3. **判断**：観点ごとに、「この観点で、読む人・変える人を助けているか」を、言葉で判断する。軽い指摘が数件あっても、全体の型がそろっていれば、良い。1 件でも、構造に関わるなら、重い。**件数や点数を、目標にしない**。
4. **優先**：影響（変更が波及する範囲・誤りの起きやすさ）が大きく、直しやすいものから。構造の指摘（責務・依存の向き）と、局所の指摘（名前・分岐）の、両方を扱う。
5. **直す**：Issue サイズの小さな変更ごとに（[進め方](../AGENTS.md)）。**動作を変えない**。直す前に、守る振る舞いを確かめるテストがあるかを見る（無ければ、先に、利用者に見える振る舞いを確かめるテストを足す。配線・文言を固定するテストは足さない）。直したら、単体テスト・E2E を通す。**機能の追加・仕様の変更を混ぜない**。

## 観点

| 観点 | 見るもの | 見ないもの（問題にしない） |
|---|---|---|
| **責務と依存の向き** | 依存が下向きだけか（App・CLI → Session → Transcription・Decision・Hub・Platform → Core）。`Core` が AppKit を `import` していないか。状態の所有者が 1 か所か（構成説明の表と一致するか）。1 つの型・ファイルが、無関係な理由で変わる責務を抱えていないか | 意図した窓口（ファサード・再公開）。名前や置き場所の好みだけの違い |
| **抽象の見合い** | 中継するだけで、方針・変換・検査を足さない型や関数。実装が 1 つで、差し替えの必要がない protocol。「util」「helper」に、無関係なものが集まっていないか。呼び出し側が、本来の入口を迂回していないか | テストのための差し替え口（偽物を差せる境界）。外部の変化を隔てる薄い層 |
| **失敗の扱いの一貫性** | `Result`・`throws`・`nil` の混在。エラーが、境界で、原因を失って包み直されていないか。握りつぶし（記録するだけで、止めも回復もしない）。失敗が、成功に見える代用品に置き換わっていないか。利用者への見せ方を、境界（CLI・UI）以外が決めていないか | 最上位の、意図した受け口。層ごとに戦略が違うこと（Core は `Result`、CLI は終了コード、など） |
| **名前と契約** | 名前と振る舞いの不一致（`get…` が状態を変える、`is…` が真偽でない）。何もしないことを隠す名前（`process`・`handle`・`manage`）。型・戻り値・コメントが、実際の動作と食い違っていないか。同じ概念に、複数の語が使われていないか（SPEC の用語に合うか） | 短い名前が、一貫した慣習として使われているもの（ループの `i`・`ctx` など） |
| **論理の明快さ** | 到達しない分岐・両側が同じ分岐・常に真（偽）の条件。不要な `async`。単純にできる真偽の式。深い入れ子（早期の `return` で平らにできるか）。1 つの関数が、複数の理由で、長くなっていないか | 意図を説明するコメントつきの空の分岐。単一の責務で長い関数。**細かく割ること自体を目的にしない**（割りすぎも欠点） |
| **古い経路の残り** | 切り替えの後に残った、旧い経路・別名・再公開・互換の層（「クリーンな切り替え」の規則）。使われない設定の項目・型・文言。新旧が同居している API | 外部の利用者が、実際にいる互換（保存された設定の引き継ぎなど。理由が、コード・文書に書いてあるもの） |
| **コメントと文書** | 実態とずれたコメント・文書。コードの言い換えだけのコメント。複雑な箇所（アルゴリズム・規則の根拠）に、理由が無いこと。構成説明・SPEC が、実装と合っているか | 「なぜ」を書いたコメント。文書の見出し・区切り |
| **テストの質** | 利用者に見える不具合（状態遷移・境界・失敗）を捕まえるか。実装の細部が変わると壊れるテスト。配線・文言・仕様の転記を固定するテスト（置かない規約）。時間・順序・外部の状態に依存する、不安定なテスト | 意図して置いていない低価値の領域（値だけの型など） |

目印に使える確認（読むための入口で、結論ではない）：`grep -rn "import AppKit" Sources/MeetingAnalyzerKit/Core`（依存の向き）、`grep -rn "try?" Sources`（握りつぶしの候補）、`grep -rn "TODO\|FIXME\|deprecated" Sources`（古い経路・保留）、型の宣言と参照の数（実装が 1 つの protocol の候補。`xd://lsp` の参照）。

## やらないこと

- **スコアや件数を、目標にしない**。警告を抑える・テストを通すためだけの変更は、直したことにならない。
- **将来のための抽象・設定・互換の層を、足さない**（YAGNI）。観点に当てはまる「足りないもの」は、実際の必要が確認されてから。
- **SPEC の要件・数値を、リファクタリングの都合で変えない**。要件に影響する判断は、利用者の判断を反映して、SPEC を更新する。
- **動作確認なしに、リファクタリングの成功を宣言しない**。単体・E2E の結果と、確認していない範囲（人間の確認が要るもの）を、分けて残す。
- 変更の対象外の、利用者の既存の変更・無関係な整理を、混ぜない。

## エージェントへの依頼の例

```text
<対象の Module・ファイル> を、docs/refactoring.md の観点で見直してください。
まず、コードを直接読んで、観点ごとに根拠（ファイルと行）を集めてください（ここまで、変更しない）。
次に、観点ごとに判断し、影響が大きく直しやすいものから、Issue サイズの変更に分けて提案してください。
私が選んだものだけ、動作を変えずに直し、単体テストと E2E で確かめてください。
```

## 結果の残し方

mikan の Issue の Report に、対象・指摘（根拠つき）・実施した変更・確認（単体・E2E）・見送ったものと理由・未確認を残す。構成の理由が変わったときは、[構成説明](architecture.md) を同じ変更で更新する。
